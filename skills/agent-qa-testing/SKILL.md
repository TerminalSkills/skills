# agent-qa testing

## Overview

Use agent-qa to write and review web, Android, and iOS regression tests. Work with the project's existing targets and model configuration. Its memidex store retains verified app facts, cautions and procedures between runs; later runs can use that knowledge to navigate the app and avoid known mistakes. Proposed updates are checked against execution evidence before promotion, and contradictory evidence can revise earlier knowledge.

## Instructions

### 1. Establish the test scope

- Locate `agent-qa.config.yaml` and the requested test or suite. Run from that project directory; a global `--config <path>` must appear before the command.
- Use the project's installed version and package manager. The examples below assume an npm installation and use `--no-install` to avoid downloading a different version. Replace `tests/checkout.yaml` with the selected test path.
- agent-qa requires Node.js 24+. If it is not installed or initialized, use the [official quickstart](https://vostride.com/docs/agent-qa/quickstart) and the user's chosen provider; preserve existing configuration and credentials.

```sh
npx --no-install agent-qa --version
npx --no-install agent-qa run --help
```

### 2. Write the test

Use the [test-authoring guide](https://vostride.com/docs/agent-qa/guides/first-test) and [test-file reference](https://vostride.com/docs/agent-qa/configuration/test) for the installed version. A v0.3.x test has:

- `test-id`: a stable, unique identifier generated by agent-qa's authoring tools. Prefer the `agent_qa_write_test` MCP tool when available. If writing YAML manually, omit this field initially and open the dashboard's Tests page to let it assign the ID before validation. Preserve an existing test's ID when editing it.
- `name`: the flow's readable name.
- `target`: an existing name in `registry.targets` in `agent-qa.config.yaml`; the target selects the app and platform. A suite may override it.
- `steps`: an ordered list of natural-language strings. Each step should state the action and the exact visible result to verify. Assertions belong in these strings, such as "verify the subtotal is $24.00".
- Optional `context` for background, `setup` for existing hook IDs, `use` for execution options, and `meta` for test metadata. Add only fields supported by the installed version and already-authorized project setup.

Common mistakes: an unquoted colon can turn a YAML string into a mapping; use quoted strings or `>-` blocks. An invented target or a copied test ID will not identify the intended test correctly. Replace vague checks such as "checkout works" with exact item names, quantities and amounts. Never weaken an assertion just to obtain a pass. Keep credentials in the project's supported secret references, outside the test text.

### 3. Validate before executing

```sh
npx --no-install agent-qa validate tests/checkout.yaml
npx --no-install agent-qa run tests/checkout.yaml --dry-run
```

Validation checks configuration, test structure, and references. A dry run lists the selected tests without executing them. Neither proves that an application flow passes. Check the selected target and test files before running; omitting the path runs all discovered tests.

For suite selection or mobile device overrides, consult the installed command's help and existing project configuration. `doctor` can help diagnose setup failures, but its checks may contact the configured model provider.

### 4. Run the selected flow

Run against the environment and test data authorized by the user. Application actions can change data, and configured providers may charge for execution. agent-qa also supports local models through an OpenAI-compatible endpoint; use the project's chosen setup and consult [Models and credentials](https://vostride.com/docs/agent-qa/configuration/models) rather than assuming a paid API is required. Local-model application execution still needs verification for the selected model and target.

```sh
npx --no-install agent-qa run tests/checkout.yaml --junit-output results.xml
```

Preserve the exit status and report path. Exit `0` means passed or healed; `1` covers failed or timed-out tests and missing required files; `2` means agent-qa could not run; `130` means cancelled. Inspect the verdict to distinguish a clean pass from a healed run; treat setup failures as unresolved execution, not application failures.

### 5. Triage from recorded evidence

```sh
npx --no-install agent-qa runs list --verdict failed --limit 10 --json
npx --no-install agent-qa runs overview RUN_ID --json
npx --no-install agent-qa runs knowledge RUN_ID --json
npx --no-install agent-qa knowledge inspect --json
```

Replace `RUN_ID` with the relevant recorded run ID. Use `runs list --json` without the verdict filter when investigating a healed run or another outcome.

If a run has no completed verdict or its knowledge view reports `evidence-incomplete`, report that gap. Do not infer a completed application outcome from an incomplete record.

Read the failed step and available evidence before proposing a correction. Edit tests or application code only when the user has authorized that change. Distinguish an application defect, a test expectation problem, and an environment/provider failure. Use the run's knowledge view to see what memidex supplied or learned. Do not erase the cache or knowledge store merely to obtain a passing result.

### 6. Verify and report

Rerun the selected flow after an evidence-based correction. Stop and report an unchanged failure when no new corrective action is justified. Report the command, run ID, verdict, relevant evidence/report paths, and what remains unverified; redact credentials and sensitive application data.

## Examples

These examples describe expected reporting for a staging shop. They are illustrative, not results of an application run performed for this contribution.

### Example 1: Add a cart-quantity regression test

**Input:** "The staging shop's Everyday Ceramic Mug costs $12.00. Add a regression test that changes its cart quantity from one to two and checks the $24.00 subtotal. Use the existing `shop-web` target; stop before placing an order."

**Test file:** `tests/checkout.yaml` after the authoring tool assigns its ID. The ID shown below is illustrative; preserve the one generated for the actual test.

```yaml
test-id: t_cart-checkout-review-local-mug-quantity-total-visible-flow-check
name: Cart quantity updates the subtotal
target: shop-web
context: The staging shop sells Everyday Ceramic Mug for $12.00. Do not place an order.
steps:
  - >-
    Add Everyday Ceramic Mug to the bag, open the shopping bag,
    and verify it contains one Everyday Ceramic Mug with a $12.00 subtotal.
  - >-
    Change the mug quantity to 2. Verify the bag shows quantity 2
    and an item subtotal of $24.00.
  - >-
    Continue to the order review and verify it lists two Everyday Ceramic Mugs
    with an item subtotal of $24.00. Stop before placing the order.
```

**Commands:**

```sh
npx --no-install agent-qa validate tests/checkout.yaml
npx --no-install agent-qa run tests/checkout.yaml --dry-run
npx --no-install agent-qa run tests/checkout.yaml --junit-output results.xml
```

**Expected report if the recorded verdict is `passed`:** "Cart quantity updates the subtotal passed: the bag and order review both showed quantity 2 and an item subtotal of $24.00. No order was placed. The JUnit report is `results.xml`." Include the actual run ID and recorded evidence paths. If the verdict is `healed`, report it as healed; validation or a dry run alone is not a pass.

### Example 2: Triage a failed quantity check

**Input:** "The checkout test failed after changing the quantity. The recorded screenshot shows quantity 2 but the subtotal is still $12.00. What should we fix?"

**Actions:** Read the supplied run's overview, failing step and screenshot. Confirm that the target is the intended staging shop and that the recorded action changed the quantity. Check the run's knowledge view for relevant earlier cautions. Compare the observed $12.00 with the test's $24.00 expectation before proposing a cause.

**Expected report for that evidence:** "The quantity check failed: quantity 2 was visible, but the subtotal remained $12.00 instead of $24.00. Inspect the cart's subtotal update before changing the expectation. Keep the test's $24.00 assertion and rerun after an authorized correction." Attach the actual run and step evidence; do not claim a root cause from the screenshot alone.

If the run ended before a verdict or its knowledge record reports `evidence-incomplete`, report the missing evidence instead. An empty failed-run list does not establish a pass.

## Guidelines

- Use this skill for agent-qa projects. For Playwright test authoring, use `playwright-testing`; for framework-level refactoring regression coverage, use `regression-tester`.
- Validation and dry-run selection can be checked locally without executing the application or invoking a model. Execution may use a local model or a separately billed provider.
- Treat missing evidence as unresolved. A healed verdict, cancelled run, setup failure, and clean pass are different outcomes.
- Do not expand the test scope, edit application behavior, overwrite configuration, or change credentials without authorization. Preserve failures and propose a correction when fixes are outside scope.
- Reports and screenshots may contain sensitive application data. Redact credentials and private data before sharing evidence.
- These original instructions use this repository's Apache-2.0 license. The separate agent-qa package uses FSL-1.1-ALv2; model, browser, and device providers have their own requirements and costs.
