# Design a SaaS Architecture for a Blender Add-on Marketplace

## The Problem

You want to build a marketplace where Blender artists sell and distribute add-ons. The challenges span two domains that rarely overlap: SaaS platform architecture (multi-tenancy, billing, license management) and Blender add-on development (extension packaging, version compatibility, viewport performance).

The platform must handle license validation from within Blender sessions, distribute version-compatible packages, and provide seller dashboards. The add-ons must follow Blender's packaging conventions and handle installation and license checks without degrading the 3D viewport. A synchronous HTTP call during a license check that freezes Blender's interface for 2 seconds makes the marketplace unusable for artists working on complex scenes.

## The Solution

Use the **saas-architecture-advisor** skill to design the tenancy, billing and API layers. Use the **blender-addon-dev** skill to build the client as a Blender 4.2+ extension (`blender_manifest.toml`), so Blender itself handles install, update and version filtering through a custom extensions repository.

## Step-by-Step Walkthrough

### 1. Decide how add-ons reach Blender

The official Blender Extensions Platform only accepts free, open-source extensions (add-ons must be GPL-3.0-or-later; see docs.blender.org/manual/en/latest/advanced/extensions/licenses.html), so a paid marketplace runs its own repository. Blender supports two kinds (docs: "Creating an Extensions Repository"): a **static** `index.json` generated by `blender --command extension server-generate --repo-dir=/path/to/packages`, and a **dynamic** one that serves the same JSON on demand. A dynamic repository receives `blender_version` and `platform` query parameters and an optional `Authorization: Bearer <access token>` header, which is exactly what a paid catalog needs.

> Design a SaaS architecture for a Blender add-on marketplace. Sellers upload extension zips, set pricing, and view analytics. Buyers purchase and install in Blender. The platform needs: multi-tenant seller dashboards, Stripe Connect payouts, license keys, CDN distribution, and a dynamic Blender extensions repository that authenticates buyers with a per-user access token.

A reasonable result: one shared PostgreSQL database with a `seller_id` column on every tenant table and row-level security (the advisor's "shared everything" model fits hundreds of sellers; per-seller databases do not); Stripe Connect destination charges with an application fee for the platform cut; an `/api/v1/extensions/` endpoint that reads the bearer token, looks up the buyer's purchases, and lists only the latest compatible version of each owned add-on for the requested `blender_version` and `platform`; downloads through short-lived signed CDN URLs. Because the listing is filtered per token, one repository serves every buyer.

### 2. Validate uploads from the manifest

Sellers upload an extension zip. Run `blender --command extension validate <folder-or-zip>` in the upload pipeline (Blender 4.2+; it parses the manifest, rejects an invalid `id` and reports a missing `__init__.py`, but does not run the add-on) and read `blender_manifest.toml` to get `id`, `version`, `blender_version_min`, optional `blender_version_max` and `platforms`. Those values drive the listing filter. Legacy `bl_info` add-ons still load but are not served by repositories, so ask sellers to convert them (remove `bl_info`, add the manifest).

> Write the upload validator: unzip, parse blender_manifest.toml with tomllib, reject a missing id/version/blender_version_min, run `blender --command extension validate`, then store the manifest fields on the version row.

Do the unzip in a sandboxed worker with size limits, and never execute seller code outside Blender's validator.

### 3. Build the client add-on as an extension

The client is itself an extension: a `blender_manifest.toml` with `type = "add-on"` and a `[permissions]` table declaring `network = "Check license and updates"` (each reason up to 64 characters). Blender's Get Extensions panel already browses, installs and updates from any remote repository the user adds (Preferences > Get Extensions > Repositories > Add Remote Repository, with an access token field), so the add-on does not need its own installer; it only needs a panel for sign-in and license status.

> Build a Marketplace Client extension for Blender 4.2+. It declares network permission, checks bpy.app.online_access before any request, runs requests in a worker thread, and delivers results to the UI through bpy.app.timers. It never calls bpy data APIs from the worker thread.

### 4. Make license checks non-blocking and tamper-resistant

Network calls run in a background thread; results reach Blender's main thread through `bpy.app.timers.register`, because `bpy` data is not safe to touch from other threads. Check `bpy.app.online_access` first and degrade quietly when the user has disabled online access. Sign licenses with an asymmetric key (Ed25519 or RS256): the SDK ships only the public key and verifies a signed token offline, so a cached license keeps working through an outage and a shipped client contains nothing that can mint licenses. Never embed an HMAC secret in an add-on.

> Build a small Python module sellers vendor into their extensions: validate_license() verifies a signed token against the platform public key and a cached expiry; check_for_updates() reads the repository listing; report_usage() posts anonymous counters only if the user has opted in.

Add-ons are GPL, so licensing deters casual sharing, not determined copying. Sell on convenience (updates, support, the listing) rather than on lock-in.

### 5. Seller analytics and payouts

> Design the seller dashboard: sales per add-on, installs per Blender version from repository requests, and payout history read from Stripe Connect. Compute all aggregates in the backend and send the dashboard display-ready rows.

Version adoption comes from the `blender_version` query parameter on listing requests. Verify Stripe webhooks with the signing secret and the raw request body, and make purchase fulfilment idempotent on the event ID so a retried webhook cannot issue a license twice.

## Real-World Example

Two developers building this for a hypothetical studio started with the dynamic repository endpoint and the extension manifest, and reached a working private beta with 12 sellers and 45 add-ons in their first quarter (their own numbers). Early prototypes did the license check on the main thread and the interface froze for a couple of seconds on every start; moving it to a worker thread with `bpy.app.timers` hand-off fixed that. Filtering the listing by `blender_version` meant buyers on 4.2 never saw packages requiring a newer release.
